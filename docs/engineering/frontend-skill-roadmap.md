# Frontend skill system: prioritized next steps

This roadmap follows the [discovery report](frontend-skill-discovery.md). The skill files are ready for planning and review; code-facing checks depend on a real frontend and agreed API contracts. Priorities describe the next implementation work, not a claim that the proposed features already exist.

| Priority | Next step and benefit | Prerequisite | Suggested workflow and skills |
| --- | --- | --- | --- |
| **P0 — Blocking** | Restore remote Git access before starting a latest-main feature branch. This makes the baseline verifiable and protects the current untracked `.agents/` and `yeu_cau.md` work. | Network/DNS and repository SSH access; clean or safely separated working tree. | `frontend-git-flow` during `frontend-feature-workflow` Scout. |
| **P0 — Blocking** | Reconcile the public gateway route/versioning, session/CSRF, resource DTOs, errors, and authorization contract for the first browser flow. This prevents a UI that appears integrated against proposal-only endpoints. | Identity, Tenant, Document, and Chat owners publish checked-in contracts and working handlers; decide PDF versus DOCX and ingestion display states for upload. | `frontend-feature-workflow` BA/Analyze with `frontend-api-integration`, `frontend-forms`, and `frontend-security`. |
| **P0 — Blocking** | Scaffold and register `apps/web` before claiming frontend build, typecheck, lint, or test verification. This makes Cook and Test executable for real UI work. | Confirm the planned React/Vite/TypeScript choice, package scripts, routing, and minimum design direction. | `frontend-feature-workflow` with `frontend-architecture`, `frontend-ui-engineering`, and `frontend-testing`. |
| **P1 — High value** | Establish a small token and component foundation for shell, navigation, forms, status, and feedback states. This reduces visual drift as RAG pages grow. | Running frontend; representative screens and design decisions. | `frontend-ui-engineering` and `frontend-forms`; verify with `frontend-testing`. |
| **P1 — High value** | Deliver the first contracted course-material journey: session, course context, text-PDF upload/status, chat answer/citation/feedback. This proves the main RAG value through a complete flow. | P0 contracts and services, safe content rendering, test environment. | `frontend-feature-workflow` with `frontend-api-integration`, `rag-chat-experience`, `frontend-security`, and `frontend-testing`. |
| **P1 — High value** | Add baseline unit/component tests and a few critical browser journeys, plus accessible and responsive checks. This makes regression evidence available for future changes. | Running frontend and stable UI/API contracts. | `frontend-testing`, `frontend-ui-engineering`, `frontend-forms`. |
| **P2 — Future improvement** | Define course catalog/detail, roles, enrollment, lessons, learning paths, and progress as actual LMS product and backend contracts. This allows LMS UI to grow without inventing state. | Product decisions and Tenant/LMS service ownership; DTOs and permissions. | `frontend-feature-workflow` BA/Analyze, `lms-ui`, `frontend-api-integration`. |
| **P2 — Future improvement** | Consider chat streaming, cancellation, realtime transport, or advanced list optimization only after contracts and measurements establish the need. This avoids premature complexity. | Working RAG flow, protocol/idempotency decisions, performance baseline. | `rag-chat-experience`, `frontend-performance`, `frontend-testing`. |
| **P2 — Future improvement** | Add visual regression, frontend observability, or internationalization skills only when the deployed UI and team workflows create recurring needs. This keeps skill discovery focused. | Stable design, telemetry/privacy decisions, supported locales or repeated visual regressions. | Begin with `frontend-feature-workflow` Scout/Analyze; extend the relevant specialist only if the work becomes distinct and repeatable. |
