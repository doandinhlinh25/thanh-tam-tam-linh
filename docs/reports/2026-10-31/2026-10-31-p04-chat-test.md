## 5. Finding F1 — incomplete candidate schema accepted

- **Severity:** P1 correctness/integration security risk. Public Chat is currently fail-closed, so this is not a reachable public bypass today; it is a release blocker for the approved malformed-response criterion and for later reopening Chat.
- **Location:** `services/chat-service/app/ai/retrieval/mapper.py:10–16,37–46`; `services/chat-service/app/domain/value_objects/evidence.py:62–109`. The mapper checks only `evidenceId`, `documentId`, `text` and `retrievalScore` keys. `contracts/openapi/document.v1.yaml:243` marks `chunkId`, `documentVersion`, `documentName`, `pageFrom` and `pageTo` required too.
- **Reproduction:** HTTPX MockTransport returns HTTP 200 with `{"successful": true, "data": {"candidates": [{"evidenceId":"e1", "documentId":"d1", "text":"content", "retrievalScore":0.9}]}}`. Calling `RetrievalClient.search(...)` **returns one Evidence**, with invented defaults `document_version=1`, `page_from=1`; it should raise `RetrievalInvalidResponseException`/technical error. A direct mapper probe with `retrievalScore:"invalid"` also returns Evidence with score `0.0`, risking a false `insufficient_evidence` downstream.
- **Baseline versus COOK:** the old mapper was permissive too; the Cook diff narrows envelope checks but leaves candidate validation incomplete. Thus F1 is an unresolved pre-existing behavior against the newly approved R0 criterion, not a new public auth regression.
- **Suggested separate COOK fix:** validate all required candidate fields and their types/ranges at the Chat retrieval boundary, preserving both supported camel/snake naming where contracted. Add regression tests for missing fields and invalid scores. Do not silently synthesize citation metadata from malformed upstream evidence. Do not make the change in TEST.
